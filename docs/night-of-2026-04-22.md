## The Big Finding

**`src/lib/server/sync.ts:161`** binds `${e.date}` in the INSERT, but the client `JournalEntry` (`src/lib/types.ts:23`) has no `date` field — it was replaced by `datetime` in the v6 migration (commit `a376d07`). The `postgres` driver throws `UNDEFINED_VALUE: Undefined values are not allowed`, the endpoint returns 500, the client catches the error, entries stay `dirty: true` locally forever.

Symptoms this explains:
- The two Safari entries never reached your phone
- Any entry you've added in the last ~2 weeks probably never pushed
- The server DB likely has no new entries since the v6 migration

**Suggested fix (needs your call):**

Option A — derive `date` server-side:
```ts
${e.datetime.slice(0, 10)}, ${new Date(e.datetime)}, // date, datetime
```

Option B — drop the `date` column from client-facing sync, keep only `datetime`. Cleaner but requires a v2 server migration to drop the column, and anything reading `date` anywhere would need to change.

Option A is the 30-second fix. I'd do A before the demo, plan B for later.

**Before committing any fix**, connect to Badger Postgres and check: do your Safari entries exist in the `entries` table? If yes, the push actually *sometimes* worked and we need deeper investigation. If no (my expectation), this single bug explains everything.

## Autonomous-agent work worth pursuing

These are the agent-driven projects I'd prioritize for this repo:

**High leverage, one-shot builds:**

1. **Pre-demo smoke agent.** Runs before any demo: starts dev server, runs Playwright golden-path, diffs Postgres row counts against expectation, reports a single green/red line. Invoke via `/loop` or cron. Would have caught tonight's bug in CI weeks ago.
2. **Migration validator.** Every Dexie version bump triggers an agent that seeds old-version data, runs the upgrade, asserts new shape. Would have caught the datetime rename mismatching the server schema.

**Ongoing, low-risk background work:**

3. **Gap-closing test loop.** One builder agent per tier-A gap, one PR each, you review in the morning. Most of the remaining test gaps are mechanical.
4. **Component unit tests.** `FlowTimeline`, `AddRiverModal`, `RiverAutocomplete`, `TagInput` have zero unit coverage. Good agent work — no product decisions, just wiring.
5. **Sync-health monitor.** Nightly: pulls from prod, checks invariants (no dirty+deletedAt, no orphan tripIds, no user with zero entries older than X). Won't catch the first incident but catches silent drift.

**Not worth doing autonomously:**

- Anything that needs a dependency decision (fake-indexeddb, a Postgres mocking library, etc.). Those should be 5-minute conversations with you, not 30-minute agent detours.
- Anything touching the sync logic itself — that's an architecture area, not a mechanical one.
